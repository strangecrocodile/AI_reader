# 下一阶段开发文档

## 1. 目标

下一阶段的目标不是把所有功能一次做满，而是先把“教材学习闭环”做成一个稳定的 MVP：

1. 首页能看到当前学习教材与当前学习计划。
2. 学习页能完成 PDF 阅读、划词提问、气泡追问、AI 讲义查看。
3. 知识页能沉淀已学知识点卡片与关系图谱。

核心原则：

- 事实层以 RAG 为底座，保证回答能回到教材原文。
- 讲义层可以做成 LLM wiki，但它是“知识沉淀层”，不是唯一真相来源。
- Agent 负责编排学习动作，不直接控制 UI 坐标和复杂前端状态。

## 2. 当前现状

当前仓库已经具备这些基础：

- 前端：`HomePage`、`StudyPage`、`Reader`、`CoachPanel`、`PlanPanel` 等基础页面与组件。
- 后端：FastAPI + SQLite，已有教材、章节、段落锚点、讲解、学习计划等存储结构。
- 检索：已有 BM25 / RAG 雏形。
- 问答：已有基于教材上下文的溯源问答接口。

当前缺口主要是：

- 没有独立的 `KnowledgePage`。
- 划词后 AI 气泡还不是真正的“锚定浮层”。
- 没有知识点关系图谱。
- 没有持续化的追问线程、知识卡片和笔记模型。

## 3. 页面目标

### Home 页面

- 左侧：当前学习中的教材。
- 右侧：当前学习计划。
- 目标是让用户“一眼知道现在学哪本书、下一步学什么”。

### Study 页面

- 左侧：PDF 阅读器。
- 支持文本高亮、左键选中、定位原文。
- 选中文本后，在选区旁边弹出 AI 气泡。
- 气泡可拖动，可继续追问。
- 右侧：AI 讲义，展示知识点清单和每个知识点的解释。
- 下半部分：可切换为知识卡片和笔记区。

### Knowledge 页面

- 展示已学习的知识点卡片。
- 展示知识点关系图谱，类似 Obsidian 的关系视图。
- 节点要能回链到教材页、讲义卡片和笔记。

## 4. Agent 设计

建议采用“一个总调度器 + 四个窄职责 Agent”的结构。

| Agent | 职责 | 输入 | 输出 |
|---|---|---|---|
| Orchestrator | 判断当前请求走问答、规划、抽取还是回写 | 页面事件、线程状态、用户操作 | 路由决策 |
| Tutor | 负责解释教材、回答追问、给出气泡内容 | 选中文本、章节上下文、检索结果 | 可追溯回答 |
| Planner | 负责首页学习计划与章节推进建议 | 教材结构、掌握度、历史学习记录 | 学习计划 |
| Curator | 负责知识点卡片、讲义摘要、题目、笔记草稿 | 章节内容、知识点、问答记录 | 结构化学习产物 |
| Indexer | 离线解析教材、切 chunk、抽知识点、建关系 | PDF/章节/段落 | 索引、图谱、知识点节点 |

设计约束：

- Agent 输出尽量结构化，优先 JSON。
- UI 坐标、浮层位置、拖拽状态由前端管理。
- 每次回答都要附带来源锚点，不能只给“看起来像对的”解释。
- 一轮问答的上下文要绑定到 `thread_id`，不要退化成全局聊天。

## 5. 知识底座设计

建议把知识底座拆成三层：

### 5.1 RAG 事实层

用途：

- 划词问答
- 章节解释
- 原文依据回跳

特点：

- 只回答教材里能找到依据的问题。
- 如果证据不足，明确说“教材中未找到直接依据”。

### 5.2 LLM Wiki 概念层

用途：

- 生成知识点长文讲解
- 维护“概念页”
- 形成稳定的知识沉淀

特点：

- 适合展示与沉淀。
- 不适合直接充当事实检索的唯一来源。
- 需要和原文锚点、章节页码保持关联。

### 5.3 图谱关系层

用途：

- 记录前置、包含、相关、对比、例题依赖等关系
- 支撑 Knowledge 页面可视化

特点：

- 图谱不是摆设，节点必须能回到教材、讲义、笔记。
- 先做“可读、可点、可回跳”，再追求复杂算法。

## 6. 数据模型建议

在现有 `books / chapters / sections / anchors / explanations / plans` 之上，下一阶段建议补这些实体：

- `concepts`：知识点节点。
- `relations`：知识点之间的关系。
- `threads`：围绕某段原文的追问线程。
- `cards`：知识卡片。
- `notes`：用户笔记。
- `questions`：系统生成题目与用户作答记录。
- `mastery`：知识点掌握度。

推荐先继续沿用 SQLite，把结构先跑通；等数据量和检索需求上来，再考虑向量库或独立图数据库。

## 7. 开发顺序

### 第 1 周

- 做好 PDF 阅读器中的文本选区与高亮锚点。
- 选中文本后，能在原位置弹出 AI 气泡。
- 气泡可拖动，支持基础追问。

### 第 2 周

- 把问答链路改成线程化。
- 让回答流式返回。
- 右侧讲义面板能展示结构化知识点清单。

### 第 3 周

- 落知识点、卡片、笔记的数据结构。
- 增加自动讲义生成与题目生成。
- 让学习结果能回写到知识库。

### 第 4 周

- 实现 Knowledge 页面。
- 画出知识点关系图谱。
- 补齐体验细节、测试与演示数据。

## 8. 重点风险

1. 不要先做“一个会自己思考很久的大 Agent”，容易失控。
2. 不要先做完整 wiki 代替 RAG，容易丢证据。
3. 不要一开始就引入太多存储和检索组件，容易拖慢开发。
4. 不要把知识图谱做成纯装饰图，节点必须服务学习动作。

## 9. 成功标准

- 用户能在首页选书，在学习页完成阅读、划词、追问、回看。
- AI 回答能清晰落到教材原文。
- 已学知识点可以沉淀成卡片与图谱。
- 系统能稳定支撑一个月内的演示版本。

## 10. 当前短期 MVP

本轮先交付一个可演示的垂直切片：

- 后端新增 `GET /api/books/{book_id}/knowledge`，从章节讲义聚合知识点和学习顺序关系。
- 前端新增 `/knowledge` 页面，展示知识点卡片、掌握度、关系图谱和选中知识点详情。
- 知识点详情可以回到对应章节，并通过 `sourceId` 高亮对应教材原文和 AI 讲解。
- 演示模式与后端模式共用同一套 `fetchKnowledge` API，方便没有模型服务时继续开发。

后续短期目标按这个顺序推进：

1. 把 Knowledge 页当前的演示掌握度和“学习中/待学习”状态改为真实学习事件驱动。
2. 将选区问答升级为绑定 `thread_id` 的可拖动气泡。
3. 为知识点增加用户笔记和生成题目，并回写 `mastery`。
