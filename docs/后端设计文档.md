# AI讲师 后端设计文档

## 1. 定位与范围

后端负责「教材驱动的学习系统」的服务端能力，与前端 `frontend/src/services/api.js`
的接口约定一一对应。当前实现覆盖产品文档 MVP 主链路：

> 导入教材（PDF / Word / 纯文本）→ 解析章节 → 生成学习路径 → 查看章节讲解 → 溯源问答 → 知识图谱

**录入范围**：文本型 PDF（可含目录书签与插图/表格）、Word `.docx` 与旧版 `.doc`
（按标题样式识别章与节）、纯文本 `.txt` / Markdown `.md`，以及**扫描件 PDF**
（自动转 OCR 异步任务，见第 10 节）。复杂表格 / 公式 OCR 与手写内容不纳入
（产品文档 6 节明确列出范围边界）。

各格式解析后产出**同一套章节-段落-锚点模型**，下游（检索、问答、知识点图谱）不区分来源格式。

**原文版式保真**：解析阶段会把段落内的行内版式读进来（`ParsedSection.content`），
阅读页因此能还原原文件里的粗体、斜体、上下标与字号层级；插图与表格也会抽出来、
按原位置插回正文。判定口径与不变量见 4.2。

## 4. API 约定（与前端对接）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 健康检查（含 LLM 模式） |
| GET | `/api/capabilities` | 当前环境能吃哪些格式（`.doc` 依赖可选的 LibreOffice），供前端收窄 accept 与提示 |
| GET | `/api/books` | 教材列表（含章节、学习计划） |
| GET | `/api/books/{id}` | 单本教材（含 `hasSource` / `sourceFormat`） |
| POST | `/api/books` | 上传教材（multipart `file` + 可选 `title`）：支持 `.pdf` / `.docx` / `.doc` / `.txt` / `.md` → 解析入库，返回体带 `contentWarning`。**扫描件 PDF 例外**：返回 `202` + `{task}`（见第 10 节）。超过 200 MB 返回 `413`；格式不支持 `415`；扫描件但不支持 OCR `422` |
| GET | `/api/books/{id}/source` | 下载上传时留存的**原始文件**；没留存（该功能上线前导入的）返回 404 |
| DELETE | `/api/books/{id}` | 删除教材及全部下游数据（章节、段落、锚点、讲解、进度、追问线程）。**不可恢复**，且是唯一会丢弃 OCR 结果的操作；教材不存在返回 `404` |
| GET | `/api/books/{id}/markdown` | 按需渲染整本 Markdown（`text/markdown` + 附件头），每个段落前有 `<!-- page: N -->` |
| GET | `/api/ocr/tasks/{id}` | 扫描件识别任务进度；任务不存在（后端重启过）返回 `404` |
| GET | `/api/books/{id}/chapters/{cid}` | 章节内容：原文段落（锚点 + 行内版式 + 插图/表格）+ AI 讲解 + 知识点大纲 |
| GET | `/api/books/{id}/knowledge` | 知识图谱 v2：跨章概念节点 + 前置关系 + 学习顺序 + 未解析前置 + 统计 |
| POST | `/api/books/{id}/chapters/{cid}/events` | 上报学习事件（`open` / `read` / `ask` / `complete` / `quiz`）→ 重算并返回掌握度与拆分说明 |
| POST | `/api/books/{id}/chapters/{cid}/progress` | **手动覆盖**章节进度（调试/纠偏用），正常学习进度走 `/events` |
| POST | `/api/ask` | `{question, bookId, chapterId, selectedText?, threadId?}` → `{answer, sources, sourceDetails, scope, threadId}` |
| POST | `/api/ask/stream` | 同上，返回 SSE：`meta`（检索范围与证据）→ `delta`（逐块回答）→ `done`（完整回答 + 溯源锚点） |
| POST | `/api/threads` | 新建追问线程：`{bookId, chapterId, anchorId?, selectedText?}` |
| GET | `/api/books/{id}/chapters/{cid}/threads` | 本章追问线程列表（最近追问在前） |
| GET | `/api/threads/{id}` | 单条线程（含全部消息） |
| DELETE | `/api/threads/{id}` | 删除线程（连带消息） |
| POST | `/api/books/{id}/plan` | 生成/重新生成学习路径 |

前端通过 `VITE_API_BASE_URL`（见 `frontend/.env.example`）切换后端模式；
未配置时前端使用内置演示数据。

### 4.1 解析受限提示（`contentWarning`）

教材与章节列表的每本书都带 `contentWarning`（字符串，空串表示解析正常）：
解析器读不全内容时，**必须让用户知道**，而不是给一本几乎空白的教材让人猜原因。

它由两类信号合成（见 `services/ingest.content_warning_of`）：

| 信号 | 来源 | 说明 |
|---|---|---|
| 症状 | 正文总字数 < 500 | 用户能直接感知到的「怎么只有这么点」 |
| 原因 | `ParsedBook.notes` | 解析器**跳过了什么**：docx 的文本框 / 图片数量、PDF 是书签还是字号推断、是否只扫了前 200 页、平均每页字数是否低到像扫描件、是否因页数超限跳过了表格提取 |

注意「表格」已不在「跳过了什么」之列：表格现在会被抽成 `kind='table'` 的段落
（见 4.2），文字进正文与检索；仍读不到的只剩文本框，以及图片里**印着的文字**
（图片本身会被落盘渲染，但里面的字不参与检索）。

字数阈值 500 有数据依据：`tools/kb-agent` 的样例教材正文只有 523 字，是合法可用的
薄教材，纯按字数判断会误伤团队自己的演示材料。因此**字数只负责触发提醒，
说明原因的是解析器报告的结构信号**。

持久化在新增列 `books.content_warning`；`Database.init()` 会用
`PRAGMA table_info` + `ALTER TABLE` 补列，老库无需手工迁移。

### 4.2 原文版式保真（`ParsedSection.content`）

段落除纯文本 `text` 外，多了一个可选 `content`，用来承载原文件里的版式信息：

| 形状 | 来源 | 说明 |
|---|---|---|
| `{runs: [{text, style: [...]}]}` | PDF span / Word run | 段落内的行内片段 |
| `{asset, width, height}` | PDF `extract_image` / Word `w:drawing` | 插图，落盘在 `data/assets/` |
| `{rows: [[{text}]], header}` | PDF `find_tables` / Word `w:tbl` | 表格，`header` 表示首行是列名 |

`style` 是一份**语义 token 白名单**（见 `parsing/base.STYLE_TOKENS`）：
`b` 粗体、`i` 斜体、`sup` / `sub` 上下标、`lg` / `sm` 比正文大/小一号。

刻意**不把字体名透传到前端**：同一本教材里就有 `SourceHanSerifCN`、`STIXTwoText`、
`FZSSJW--GB1-0` 好几种字体，透传会变成一组不可控的字体加载；而阅读页的观感本就由
`.paper` 的 CSS 决定，前端只按 token 加 class。字号同理只保留**相对层级**——
PDF 的字号是打印单位，绝对值没有意义。

**核心不变量：`"".join(run.text) == section.text`。** 检索、锚点、划词定位全都建立在
`text` 上，`content` 只是额外的渲染信息；两者一旦不一致，就会出现「渲染出来的字和
能选中的字不是同一批」这种极难排查的问题。所以每个来源都保证这一点，并有断言覆盖。

三种来源的样式判定：

| | 粗体 | 斜体 | 上下标 | 字号档位 |
|---|---|---|---|---|
| PDF | `flags & 16` 或字体名含 Bold/Black/Heavy | `flags & 2` 或字体名含 Italic/Oblique | 与所在**块**的正文基线偏移超过字号 0.3 倍 | 相对全书正文基准字号（span 中位数） |
| Word | `run.bold` | `run.italic` | `run.font.subscript / superscript` | 相对**众数**字号 |

两处容易踩的坑，都已按上面的口径处理：

- PDF 的基线必须按**块**（一段文字的容器）算，且取**最大字号** span 的原点。
  按行算时「下标独占一行」会失去参照；按「出现最多的 y」算时上标与正文各出现一次
  会打成平手，取谁全凭字典序。
- Word 的正文基准字号取**众数**而不是中位数：Word 里字号只在显式设置过的地方才有值，
  样本很稀（可能只有标题的大字号和正文各一次），中位数会被大字号带偏，
  把正文自己判成 `lg`。

**插图与表格的开销差两个数量级**（实测同一本 444 页教材：`get_images` 0.4 ms/页，
`find_tables` 74 ms/页 —— 全书提表格要 33 秒）。因此 `parsing/assets.py` 把两者拆开，
并按 `TABLE_SCAN_MAX_PAGES`（200 页）决定做到哪一步：超限的书只提图，
并把这件事实写进 `notes` → `contentWarning`，**不静默降级**。

**向后兼容**：`content` 为空表示「没有额外版式」，此时渲染层把 `text` 当成单个纯文本
片段。纯文本 / Markdown 教材、以及本次改动前入库的老数据都走这条回退路径，
因此不需要任何数据迁移。

存储上 `sections.content` 列存 JSON 字符串（走同一套 `_ADDED_COLUMNS` 补列机制），
`sections_of` 读出来即解成 dict；空串或坏数据一律当「无版式」，不让一行脏数据炸掉整章。

## 5. 溯源问答（核心链路）

```
question
   │
   ├─ ① 本章检索（BM25 + 可选向量融合）
   │      └─ 本章最佳命中覆盖率 ≥ 0.22 ──► scope = chapter
   │
   ├─ ② 本章依据不足 ──► 扩展到全书检索（同一套 BM25/向量，允许列表放到整本书）
   │      └─ 命中可能来自其他章节 ──► scope = book
   │
   ├─ 覆盖率仍 < 0.22 ──► 「教材中未找到直接依据」（不编造）
   │
   └─ 有证据 ──► 提示词（片段编号 [1][2]…，标注章节名）
                 │
                 ├─ 非流式：一次生成
                 └─ 流式（/api/ask/stream）：meta → delta* → done
                 │
                 ▼
        溯源锚点由回答里的 [n] 反查证据得出（不信任模型自报 id）；
        没有引用则回退到第一条证据
                 │
                 ▼
        {answer, sources:[锚点id], sourceDetails:[{id, page, text, chapterId, chapterTitle}], scope}
```

- 锚点 id 与段落 id 相同（如 `b1-s2-9`），前端同章直接定位高亮；
- `sourceDetails` 带 `chapterId` / `chapterTitle`，**跨章依据**由前端跳到对应章节再定位；
- `scope=book` 表示「本章没讲清楚，答案依据来自全书检索」，前端会显示提示；
- 章节重新导入会调用 `retrieval.invalidate_book` 清掉该书的 BM25/向量缓存；
- **无模型 / 模型调用失败时不做生成**：兜底答案只列检索到的教材原文（逐条带 `[n]` 编号，
  仍可溯源回跳），并注明当前未接入大模型。**不返回与教材无关的通用讲解**——这条和
  「教材中未找到直接依据」是同一条产品边界（见 `产品设计文档.md` 第 4.4 节），
  兜底路径同样不许越过。

## 6. 知识图谱（概念层 v2）

契约与 `tools/kb-agent` 的 `extract.py` / `graph.py` 对齐（该组件依赖 LangChain 等重型
依赖、独立虚拟环境，后端这里自研轻量实现，**不引入它的依赖**）：

```
章节锚点段落 ──► LLM 结构化抽取 {concept, definition, prerequisites, example, anchors}
             │     （anchors 只能取本章真实锚点，禁止编造；每章 ≤12 条）
             ├─ 无 Key / 输出非法 ──► 规则回退（强标记词定位定义句，确定性可测）
             ▼
        concepts 表按 (book_id, chapter_id) 缓存（只抽取一次）
             │
             ▼
   跨章按概念名合并节点 ──► 前置边（source 依赖 target）
                       ├─► 同章相邻概念补「学习顺序」边（已有前置边则不重复）
                       └─► 找不到的前置概念归入 unresolved（前端标为教材外）
```

`GET /api/books/{id}/knowledge` 返回：

| 字段 | 说明 |
|---|---|
| `concepts[]` | 节点：`id/title/label/definition/summary/prerequisites/chapters/anchorCount/anchors/chapterId/chapterTitle/sourceId/sourceLabel/status/mastery/method` |
| `relations[]` | 边：`{id, source, target, type: prerequisite\|sequence, label}` |
| `unresolved[]` | `{name, requiredBy[]}` —— 前置概念在本教材里找不到（表述差异或未入库章节） |
| `methods` | 本次图谱用到的抽取方式：`llm` / `rule` |
| `stats` | `conceptCount / learnedCount / relationCount / prerequisiteCount / unresolvedCount` |

其中 `title/summary/chapterId/chapterTitle/sourceId/status/mastery` 是升级前的兼容字段，
前端可零改动读取；`sourceId` 一定是该章真实存在的锚点，保证节点能回跳教材原文核对。

## 7. 掌握度计算（可解释）

掌握度**不是前端写死的数字**，而是由学习事件算出来的：

```
open（进入章节） / read（读到段落，带锚点 id） / ask（提问，记问题原文）
complete（标记学完） / quiz（自测作答，带对错）
        │  写入 learning_events（read 按锚点去重、ask 记原文用于去重）
        ▼
services/progress.py 按公式重算
        │
        ▼
chapter_progress（只增不减） ──► 知识点卡片掌握度 / 教材总进度（各章平均）
```

| 分项 | 定义 | 权重 | 防刷分约束 |
|---|---|---|---|
| 覆盖度 | 读过的正文段落数 / 本章正文段落总数 | 50 | 只认本章真实锚点，乱报不计分 |
| 互动度 | min(不同提问数, 5) / 5 | 25 | 同一问题只算一次，封顶 5 次 |
| 自测正确率 | 答对题数 / 答题总数 | 25 | 无自测记录时该项权重按比例并入前两项（覆盖度 66.7 / 互动度 33.3） |

- 状态规则：`complete` 事件或掌握度 ≥ 80 → `learned`；有任意事件 → `learning`；否则 `planned`；
- 掌握度只增不减（`chapter_progress` 取 max），因此接口同时返回
  `computed`（本次按事件算出的值）与 `mastery`（实际生效值）；
- `/events` 返回值含 `breakdown`（每项的权重与得分）与 `signals`（读了几段、提问几次…），
  前端据此展示「掌握度是怎么来的」；前端演示模式用 `frontend/src/services/progress.js` 实现同一套公式。

## 8. 追问线程（划词气泡的持久化）

一次划词 = 一条线程：气泡里的所有追问都落在同一条线上，刷新页面 / 切回章节仍可回看。

```
选中原文（带锚点 id）
   │  POST /api/threads
   ▼
threads(id, book_id, chapter_id, anchor_id, selected_text, created_at, updated_at)
   │  POST /api/ask(/stream) + threadId
   ▼
thread_messages(thread_id, role, text, sources, detail{sourceDetails, scope}, created_at)
```

约定：

- 线程绑定 `(book, chapter, 锚点, 选中原文)`；**带 `threadId` 提问时检索范围以线程所属章节为准**
  （防止把线程的追问算到别的章节头上）；
- 流式提问先落「问题」再生成（流断也不丢问题），收尾落「回答」；
- 标题：优先取选中原文（截断 24 字），否则取第一个问题；
- 气泡位置、拖动状态由前端管理，**不入库**（见 `docs/下一阶段开发文档.md` 第 4 节约束）；
- `updated_at` 为微秒精度，保证「最近追问」排序可区分。

## 10. 扫描件 OCR（可选能力）

### 10.1 为什么单独放一个可选依赖

OCR 依赖（`rapidocr` + `onnxruntime`）有 100 MB 上下，而「不装模型、不配 Key 就能跑通演示」
是本项目的核心卖点。所以它躺在 `requirements-ocr.txt` 里，没装时 `/api/books` 对扫描件
返回 **422 + 一条带安装命令的提示**（`SCANNED_NO_OCR_MESSAGE`），而不是含糊的「解析失败」。
其余格式完全不受影响。

选 `rapidocr` 而不是 `rapidocr-onnxruntime`：后者声明 `python_requires < 3.13`，装不上本仓库
的开发版本（3.13.5）。3.x 的模型随 wheel 分发，**默认构造不联网**——但改
`model_type` / `ocr_version` / `lang_type` 会触发 ModelScope 下载，这三个参数永远不要传。

### 10.2 链路

```
POST /api/books
  └─ probe_pdf(data, sample_pages=12)   抽样判定是不是扫描件（阈值 SPARSE_CHARS_PER_PAGE）
       └─ 是 → OcrTaskService.submit()  → 202 {task}
                 └─ 守护线程：逐页 get_pixmap(200dpi) → PNG bytes → engine.recognize()
                       → 结构重建（见 10.3）→ store_parsed_book()（单事务）
                 ← 前端轮询 GET /api/ocr/tasks/{id}
```

几个刻意的选择：

- **不用 `BackgroundTasks`**：`TestClient` 下它会同步内联执行，测试会真跑一遍 ONNX 识别。
- **不用 `asyncio.to_thread`**：它用默认执行器（最多 32 线程），OCR 是 CPU 密集的，
  并发几本会把整个应用拖死。
- **用守护线程而不是 `ThreadPoolExecutor`**：后者的工作线程不是守护线程，解释器退出时会
  join 它们——一本 400 页的书要跑十几分钟，等于 Ctrl+C 之后进程赖着不走。
- **状态落 SQLite `ocr_tasks` 表**而不是内存字典：进程重启后内存里的任务会消失，
  前端只能显示「任务不存在」；落库则能在启动时由 `fail_stale_ocr_tasks` 诚实回报
  「服务重启导致识别中断，请重新上传」。**这一版不支持断点续跑**，也不假装支持。
- **前端轮询而不是 SSE**：进度只是一个每几秒变一次的整数，SSE 的逐字延迟优势在这里不存在；
  轮询还天然扛得住 `--reload` 和标签页休眠。

### 10.3 结构重建（这是「借 marker 思路」的地方）

文本来源不同，但结构识别整套复用已有机制：`_split_paragraphs`（按行尾标点切段）、
`_repeated_margin_lines`（剔正文内跨页重复行）、`build_blocks` / `chapter_level_of`
（层级判定与分块）都原样调用。OCR 特有的三步：

| 步骤 | 做法 | 为什么 |
|---|---|---|
| 去页眉页脚 | **按位置**切带：`y ∈ [H/16, 0.95H]` 之外的整行丢掉 | 教科书常是「奇数页页眉=章名 / 偶数页页眉=书名」，跨页重复率达不到 `_repeated_margin_lines` 的阈值，靠文本去不掉 |
| 标题判定 | `(章标题正则 或 节标题正则) 且 高度 ≥ 正文中线高 × 1.18 且 非公式 且 有实义字符` | 单一判据都会误判：只按文本会把习题首行 `4.1 设五维空间的线性方程为：` 当标题，只按几何会把公式碎片 `[Cd]` 当标题。取「且」 |
| 正文高度 | 行高取**截尾中位数**（先剔掉 > 中位数 ×1.5 的行） | 标题会拉高朴素中位数，把阈值顶到正文高度带里面 |

`H/16` 这个比值是在真实扫描教材上量出来的：页眉落在 `y₀/H ∈ [0.044, 0.052]`，正文首行
≥ 0.077，0.0625 正好卡在空隙里。取 1/12 会切进正文——实测有几页的首行在 0.077 左右，
会被整行吃掉。`test_ocr.py` 里有一条测试专门钉住这个区间。

### 10.4 页码保真

`ParsedSection.page` 本来就是真实字段，OCR 逐页处理，直接写**原书印刷页码**，
绕开了 `assemble_book` 给没有物理页码的 Word/txt 用的 `CHARS_PER_PAGE = 1200` 虚拟页码换算。
下游（`ask.py` → `sourceDetails[].page` → `CoachPanel.jsx`）一行都不用改。

难点是**印刷页码 ≠ PDF 页序**：实测那本 231 页的教材恒定偏移 −10（PDF 第 101 页印的是 91）。
做法是读页脚带里那个「孤零零的数字」（`^\d{1,4}$`），对全书求**偏移的中位数**——
个别页 OCR 错读、图版页压根没印页码都无所谓。样本不足 3 个或偏移绝对值 > 100 时判为读不到，
此时注意区分两种提示文案：

- 读到了页码 → 「页码取自原书页脚，与纸质书印刷页码一致」
- 没读到 → 「未能读到原书页码，这里的页码是 PDF 页序，可能与纸质书印刷页码不一致」

（判断条件是 `offset is not None` 而不是 `if offset:`——偏移为 0 意思是**读到了且正好对齐**，
写成真值判断会把它误报成「没读到」。）

### 10.5 失败策略：全有或全无

识别到一半失败时**一行都不写库**，任务标 `failed`，消息写清跑到第几页
（`已识别 120/400 页后失败：…`）。因为 `store_parsed_book` 在 `ocr_pdf_bytes` 完整返回之后
才被调用，而它内部是单事务——半本书入库会破坏产品最核心的承诺「每条回答都能回到原文核对」：
溯源会把 400 页书的前 120 页当成完整依据展示，而前端唯一的补救按钮是「知道了，先这样看」，
太容易被划过去。

### 10.6 Markdown 导出：按需渲染，不落库

`services/export.py::render_markdown` 是纯函数，`GET /api/books/{id}/markdown` 现算现给。
数据库（chapters / sections）是唯一权威，因为**溯源依赖它**；再存一份 md 会静默漂移。
每个段落前带 `<!-- page: N -->`，导出的文件仍然可以拿去和纸质书核对。

### 10.7 已知限制

- **单栏假设**：双栏教材的 OCR 行会交错，v1 不解决。
- **速度**：4 线程下实测约 **12.3 秒/页**（28 核机器），400 页要 80 分钟以上。
  前端有两个各自独立的判据，都**只停止等待，不判定失败**：
  等待预算按页数算 —— `max(45 分钟, (页数 + 30) × 30 秒)`；另有一条卡死检测，
  进度（`donePages`）连续 15 分钟不动即认定真卡住。放弃时会**先重读一次教材列表再提示**，
  因为「刚好在完成前一秒放弃」是真实发生过的：一本 231 页的书跑了 47 分 28 秒，
  旧的 45 分钟固定上限提前 2 分半放弃，而列表只在成功分支里刷新，教材入了库却始终不显示。
  抢到多少 CPU 也直接决定快慢，所以限制 ONNX 线程数（`AI_READER_OCR_THREADS`，默认 4；
  用 `-1` 会用满核心，在 Web 服务里是坏邻居）。
- **删教材不释放 `ocr_tasks`**：那是有意保留的任务日志，`book_id` 删后成为悬空字符串，
  没有任何代码 join 它。其余下游数据（章节、段落、锚点、讲解、进度、追问）在
  `db.delete_book` 里逐表显式删除——`sections` / `anchors` / `explanations` / `plans`
  **没有指向 `books` 的外键**，靠 `ON DELETE CASCADE` 会留下孤儿。
- **标题识别是最弱的一环**：标题判错只是章节切分变粗糙，页码与正文仍然正确，溯源仍可用——
  属于「可用但不完美」。退一步说，这一点在方案里就是明确写下的风险。
- **混合 PDF**（部分页有文本层、部分没有）会被抽样平均判为「文字版」，维持现状。
